Horodatage

Qui fait foi

Le timestamp retenu pour affichage et stockage est le timestamp serveur (serverTs), sauf si le timestamp node (ts) est fiable et récent.

Règle de sélection :

if (ts > 1_700_000_000_000 AND |serverTs - ts| < 60_000) {
    tsAffichage = ts          // horloge node synchronisée et cohérente
} else {
    tsAffichage = serverTs    // clock non synchronisée ou dérive excessive
}

Justification par acteur

ActeurRôle vis-à-vis de l'horodatageAutorité
Node (simulateur) Estampille chaque message avec son horloge locale (ts). Avant synchronisation NTP, ts = now - bootAt (valeur depuis l'époque 0, ex : 5200 ms = 5,2 s de uptime). Autorité principale si clockSynced = true
Passerelle LoRa (QUA/EXT) Ne modifie pas le ts du message. Ajoute un horodatage de transit si nécessaire (champ optionnel gwTs). Référence de transit
Adaptateur MQTT (serveur) Ajoute serverTs = Date.now() au moment de la réception du message simulateur. C'est l'horodatage de référence si le node n'est pas synchronisé. Autorité de fallback
Broker Mosquitto Ne modifie pas les payloads. Pas d'horodatage broker. Aucune
Navigateur (front web) N'horodate jamais les données affichées. Utilise uniquement tsAffichage reçu dans les messages. Aucune

Cas particuliers

Node sans synchronisation NTP (boot récent)

Le simulateur implémente : si clockSynced = false, alors ts = now - bootAt (millisecondes depuis l'epoch 0). Un message avec ts = 5200 indique un node démarré depuis 5,2 secondes. Le seuil ts > 1_700_000_000_000 (après novembre 2023) détecte ce cas et bascule vers serverTs.

Coupure réseau et bufferisation

Pendant une coupure réseau de moins de 10 minutes (exigence projet), les nodes conservent leurs mesures en RAM. À la reconnexion, les messages sont publiés avec leur ts original (horloge node). serverTs reflète le moment de réception par le broker — potentiellement 10 minutes après ts. Le serveur détecte les messages en retard par la condition serverTs - ts > 2 × period et les marque comme "late": true dans la base de données pour ne pas déclencher de fausses alertes.

Reconnexion tardive et messages en retard

Un message en retard ne doit pas déclencher une alerte "porte ouverte" si l'événement date de plus de 30 secondes. Le serveur compare serverTs - ts et ignore les alertes déclenchées par des événements arrivés plus de expiresAt secondes après leur émission.

Dérive d'horloge

Le simulateur modélise une dérive via clockDriftMsPerMin. Tolérance acceptée : ±5 secondes. Au-delà, le serveur bascule sur serverTs. La dérive est détectée quand |serverTs - ts| > 5000 malgré ts > 1_700_000_000_000.
