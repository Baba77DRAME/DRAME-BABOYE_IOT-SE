Stratégie tampon hors-ligne

Problème

Pendant une coupure réseau (broker inaccessible, perte WiFi, redémarrage Mosquitto), le simulateur continue de générer des messages. Sans tampon, tous ces messages sont perdus. Or :

  • Un événement porte ouverte non transmis peut empêcher la détection d'une surchauffe.
  • Un événement boot non transmis laisse le serveur d'alertes croire que le node est hors ligne.
  • Un ack non transmis laisse le front sans retour sur une commande.

Stratégie choisie : tampon applicatif prioritaire en mémoire

Deux files FIFO indépendantes avec capacités différentes :

FileContenuCapacité (défaut)Débordement
Haute priorité QoS 1 : door, boot, ack, availability 300 messages (60 %) Supprime le plus ancien + avertissement stderr
Basse priorité QoS 0 : telemetry, heartbeat 200 messages (40 %) Supprime le plus ancien (silencieux)

La capacité totale est configurable via MQTT_BUFFER_MAX (défaut 500).

Durée de buffering en pratique

Avec le simulateur en scénario incidents, vitesse ×60 :

Type de messageFréquence simuléeFréquence réelleVolume / heure réelle
Telemetry (28 nodes)30 s/node0,5 s/node~2 016 msg/h
Heartbeat (28 nodes)5–30 min/node5–30 s/node~112–672 msg/h
Door eventsvariablefaible< 50 msg/h

Avec le tampon par défaut (500 messages), la basse priorité couvre environ 6 minutes de coupure sans perte de telemetry. La haute priorité couvre plusieurs heures d'événements critiques.

Reconnexion — backoff exponentiel

Tentative 1 : délai = MQTT_RECONNECT_MIN_DELAY (défaut 3 s)
Tentative 2 : délai = 6 s
Tentative 3 : délai = 12 s
Tentative 4 : délai = 24 s
Tentative N : délai = min(délai × 2, MQTT_RECONNECT_MAX_DELAY)
              (défaut max = 30 s)

À chaque connexion réussie : délai remis à MQTT_RECONNECT_MIN_DELAY.

Le backoff évite de surcharger un broker en cours de redémarrage avec des tentatives répétées.

Vidange du tampon après reconnexion

  1. Reconnexion établie → événement connect
  2. Publication du LWT online et des 28 messages availability online (retain)
  3. Abonnement aux commandes rétabli
  4. drain() — les messages sont republiés en séquence, haute priorité d'abord
  5. Publication sérialisée via callback pour ne pas saturer le broker

Gestion des doublons

Chaque message porte un champ msgId (8 octets hex aléatoires, généré par l'adaptateur). Si un message QoS 1 était en cours d'envoi au moment de la coupure, il peut être republié après reconnexion. Le serveur d'alertes et le front web peuvent utiliser msgId + seq pour détecter et ignorer les doublons côté consommateur.

L'adaptateur lui-même ne déduplique pas : chaque élément du tampon est republié une seule fois.

Préservation de l'ordre

L'ordre est préservé au sein de chaque file (FIFO). Les messages haute priorité sont republié avant les basse priorité. L'ordre relatif entre un heartbeat (basse) et un door event (haute) peut donc changer si les deux étaient dans le tampon au même moment — ce qui est acceptable : le serveur utilise les timestamps ts et serverTs pour reconstituer l'ordre temporel réel.

Ce qui n'est pas perdu pendant une coupure

  • Tous les événements porte (door open/closed) — haute priorité, QoS 1
  • Tous les événements boot — haute priorité, QoS 1
  • Tous les acks de commande — haute priorité, QoS 1
  • Les messages availability — publiés à la reconnexion (reconstruit l'état)

Ce qui peut être perdu (acceptable)

  • Les lectures de telemetry les plus anciennes si le tampon basse priorité est plein (coupure longue)
  • Les heartbeats (le serveur détecte le node offline après le timeout habituel)
